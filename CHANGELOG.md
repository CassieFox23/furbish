# Changelog

Format after [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## Unreleased

### Added

- The repo base: docs, CI, and a stub CLI that answers `--help` and `--version`. No checks work yet.
- The prose reader (`read_prose`): reads the sentences out of a draft, numbers them S1, S2, …. It skips fenced code, comments, tables, `<details>` summaries and the footer, and it stays fast on hostile text. `check` uses it.
- The config loader (`find_config`, `load_config`, `pick_profile`): finds the file in the order `CONFIG.md` describes, checks every key and value, and reports a mistake with the file's path and the key at fault instead of crashing. `check` reads it.
- `furbish check DRAFT [--repo owner/name] [--post]`: prints only the problems in a draft, one per line as `path:line: message` with the sentence id where one applies, and nothing when it passes. Exits 0 on a pass, 1 on problems and 2 when it cannot run. Rules: reading grade (with `--post`, where a sentence at grade 10 or more is too hard), the `first_line_prefix`, commit shas and URLs in backticks, blank lines in `<details>`, informal licence names, `@` mentions, the TL;DR, the footer, banned phrases and private text. A 262 KB draft checks in well under a second.
- Outside checkers: `check` runs each `external` entry from the profile (`run_external`) after its own rules. `lines` mode reports the output lines that match a regex; `json` mode reads Vale's `--output=JSON`. The draft's path is the last argument, nothing runs through a shell, a checker is stopped after 60 seconds, and a checker that can't do its job ends the run with exit 2. Printed text has control characters replaced.
- `furbish set DRAFT ID TEXT [--repo owner/name] [--write]`: replaces one sentence by the id `check` prints, at its exact place in the file. The new sentence must keep every number, commit sha and inline-code span of the old one, and a sentence under a `keep_negation` heading must keep its negation; the change is also refused if the sentences around it would no longer read the same. It prints a diff, and writes the file only with `--write`, keeping its line endings and mode. Exits 0 when done, 1 when refused and 2 when it cannot run.
- `furbish fix DRAFT [--repo owner/name] [--write]`: safe mechanical edits shown as a diff and written only with `--write`. It takes the backticks off a lone commit sha or URL, puts the blank lines GitHub needs inside `<details>`, and with `code_names` in the profile turns quoted test names, CI check names and CI states into inline code. It leaves code, comments, tables, quotes, link text, headings, checkboxes, template lines and the footer alone, leaves a whole paragraph alone when anything in it can't be read safely, keeps line endings, and a second run changes nothing. Exits 0 when done (silent when there is nothing to fix), 1 when it refuses and 2 when it cannot run.

- `furbish split DRAFT [--repo owner/name]`: for each sentence at grade 10 or harder, prints the id and where it could be cut in two when both halves read at least a whole grade easier. It cuts at a semicolon, a spaced dash or a comma before and, but, so, or or yet, never inside code, links, URLs, tags or quotes, never with a bracket or emphasis left open, never in a sentence where a quote starts or ends outside it, and skips a sentence over 2,000 characters. It never changes the draft. Exits 0, or 2 when it cannot run.
- Kinds: `[repo."owner/name".kinds.NAME]` tables, picked with `--kind NAME` on `check`, `set`, `fix` and `split`, override only the keys they name and take the rest from the repo profile. `grade_skip` lists regexes for lines the reading grade leaves out; every other rule still reads them.
- `first_line_skip` in a repo profile: a regex for a whole first line, such as a row of badges, that may come before the TL;DR. When the first non-blank line matches it, the TL;DR rule reads the next non-blank line instead.
- `furbish check --text`: prints each flagged sentence, indented, under its problem, for a tool that rewrites hard sentences and needs their text, not only their id and line.
- Harper as an outside checker: `mode = "harper"` reads `harper-cli lint --format json` (checked against harper-cli 3.2.0), and `check` prints each finding with Harper's first suggestion. An entry's `fix` lists the Harper rules whose suggestion `furbish fix` may apply, only where Harper offers exactly one, only in the prose `fix` already edits, and never one that adds or removes Markdown, touches an @ mention, path or joined name, or drops a negation ("wont" included) or a number. Harper's "AN" for a capital "A" is written "An".
- Borrowed word lists in `data/`, each beside its licence, with a NOTICE: proselint's redundant phrases, wordy phrases, hedges, clichés and jargon; write-good's wordy phrases (too-wordy) and its two sentence-opener rules; and the plain phrases of vale-ai-tells. `words` in a profile turns lists on by name, and `check` then flags each phrase it finds in the prose with the list it came from. `word_swaps = true` lets `fix` make the one-for-one swaps, but never one with a negation before it in the same clause or in the phrase itself, one after "a" or "an" that would change the word the article goes with, or one in odd capitals. Both are off unless a profile sets them.
- A length rule: `check` fails a draft over 65,536 characters, the limit in GitHub's own error message ("Body is too long (maximum is 65536 characters)"), and says how far over it is and on which line it goes over. It counts the characters as written, each line break included. Whether GitHub counts bytes instead, which would make the real limit lower for text with accents or emoji, is not checked.

### Changed

- The prose reader is faster on drafts of many short lines: about 40% on a 260 KB draft of one-word lines, measured on one machine.
- Fixes from a blind review by Fable 5.1: the prose reader now skips indented code and tables that have no leading pipe, so `check`, `set`, `fix` and `split` all agree on what is prose (before, `set` could merge a pipe-less table into one sentence and rewrite it, and `check` flagged shas and mentions inside indented code); a bare sha or URL at the start of a sentence splits it the same as in backticks, so `fix` no longer joins two sentences and shifts the ids after it; a sentence made only of a bare sha is not a sentence. The reader no longer carries a grade of its own: `check` and `split` grade with one function, which also strips HTML tags and reads double-backtick code. Every kind of heading, setext included, is exempt from the grade and from `split`. `@` mentions are found next to any punctuation (not inside code, links, URLs or an email address). The TL;DR rule reads the documented `first_line_prefix` example, a byte order mark, and a heading right under the TL;DR; a `<details>` in inline code no longer turns it off. The `set` and `fix` diffs now carry `\ No newline at end of file`, so `patch` applies them. `split` offers a second half only where the reader would see a new sentence, and counts `_` and `~~` emphasis. The licence message gives an example that fits the name, and the missing-template error names the config key.
- The grade rule is now shared between `check` and `split`, so both agree on what is too hard. It now also exempts ordered task items (`1. [ ]`) and a heading or checkbox on a first line that starts with a byte order mark, and a template is read line by line on newlines only, so an odd line break inside a template line no longer splits it.
- `check` now flags an upper-case or mixed-case commit sha in backticks too, and says to write it bare and in lower case: GitHub's Markdown renderer turns a bare lower-case sha into a commit link but leaves the same sha in upper or mixed case as plain text. `fix` still takes the backticks off a lower-case sha only, since an upper-case one would not link and could be some other hex code.
- The TL;DR rule accepts the colon outside the bold, `**TL;DR**:`, as well as `**TL;DR:**`.
- A task item inside a block quote (`> - [ ] …`) is exempt from the reading grade like any other checkbox, and its `[ ]` is left out of the sentence, so `set` keeps it.
- `split` now counts the words in each half the way `check` does, by the spaces between them, so a half of two words and an ellipsis counts as three. Before, `split` counted only words with a letter or digit in them, and the two commands could disagree on which halves get a grade.
- An outside checker now runs in its own process group. When it runs too long or prints more than 64 MB, furbish stops the whole group, so nothing it started is left running, and holds no more than 64 MB of its output in memory. A program a checker leaves behind after it ends is stopped too. Stopping furbish with Ctrl-C, by closing its terminal or with SIGTERM stops the checker with it. A program that moved itself out of the group can't be stopped this way, but furbish no longer waits on it once the checker has ended. The largest Vale output measured, on a 262 KB draft made of nothing but alerts, was about 5.7 MB.
- The prose reader knows GitHub's raw HTML blocks: a line opening with a block tag such as `<div>`, `<p>` or `<details>`, or a lone tag after a blank line, starts one that runs to the next blank line, and `<pre>`, `<script>`, `<style>` and `<textarea>` run to their closing tag. GitHub shows the text in one without Markdown, so `fix` leaves it alone (before, it could add backticks that GitHub then printed), while `check` still grades it. Inside one, list and quote marks are plain text, so sentence ids can shift on such drafts. `fix` adds the blank lines inside `<details>` first and makes its other edits on the result, so text right under a `<summary>` is still fixed in one run, and it still refuses when those blank lines would change how the rest of the draft is built (indented lines turning into code, for example).
- `check` no longer asks for blank lines around a `<details>` summary inside a `<pre>`, `<script>`, `<style>` or `<textarea>` block, and `fix` no longer adds them. GitHub shows the text in such a block as it is, so the blank lines would only have shown up as empty lines. Both now take where such a block starts and ends from the prose reader, so the three can't disagree about it, and neither asks for a blank line that would only land inside such a block once the others are in. The reader now does what GitHub does inside one: it looks only for the closing tag, so a code fence, comment, summary or indented line inside no longer hides it, and a `<pre>` after a comment on the same line, or inside a fence, comment or indented code, starts nothing. Sentence ids can shift on drafts with such a block. This covers blocks that start at the left margin, not inside a list item or a quote.
- A footnote definition's label (`[^1]:`) is left out of its sentence, as a list marker is, so it no longer counts as a word and `set` keeps it.
- Link text that holds an escaped bracket or a code span with a bracket in it is now read as one link, which `fix` and `split` both rely on.
- The prose reader no longer counts horizontal rules, empty list items or link definitions as prose, reads a line underlined with `===` or `---` as a heading, accepts headings indented up to three spaces, ignores a byte order mark at the start of the file, and leaves a checkbox, a list marker inside a quote or a tab after a list marker out of the sentence. Sentence ids can shift on a draft that has link definitions, which used to be numbered.
- The licence message for a GPL name now fits its family and version. `GPLv3` gets `GPL-3.0-only`, or `GPL-3.0-or-later` if any later version is allowed too; `LGPLv2.1+` and `GPLv3 or later` get the `-or-later` id; `Lesser GPL`, `Library GPL` and `Affero GPL` count as LGPL and AGPL; and a version that doesn't exist, such as `GPL v4` or `GPLv2.1`, gets no made-up id. Only the digits 0 to 9 count as a version. Before, every GPL name got `GPL-2.0-only` as its example.
- `check` no longer asks for a blank line before `</details>`, and `fix` no longer adds one. GitHub's own renderer shows a fold the same with or without it, whatever comes right before the closing tag: bold text, a paragraph, a list, a table, a quote, a heading, a code fence, indented code, a `<pre>` block or a fold inside a list item (checked through GitHub's Markdown API on 14 Nov 2026). The blank line after `</summary>` is still needed and still checked.
- The `write-good` word list now has the 27 weasel words of the weasel-words package that write-good uses (MIT; the 26 of its 0.1.1 release on npm, plus "usually" from its repo), vague words such as "very", "many", "clearly" and "is a number". `check` says each one is vague and to say exactly what is meant or cut it. As in write-good, "too many" and "too few" are not flagged; a list can now hold rows like these, of the kind `none`, that flag nothing and keep the word inside them from being flagged, while a longer phrase from another list that starts inside one, such as "few in number", is still flagged and swapped. `fix` has no swap for any weasel word.
- A `diction` word list: 26 clichés from GNU diction 1.11 (GPL-3.0-or-later), such as "par for the course" and "easier said than done", the ones proselint's GNU diction check uses. The 27th phrase in proselint's copy, "we regret to inform you", is not in GNU diction, so it joins the `proselint` list instead. Off unless a profile names it.
- The length rule now counts UTF-8 bytes, not characters: a plain letter is 1 byte, an accented letter 2 and an emoji 4, and the message says so. GitHub's error message says "characters", but which it counts isn't documented and wasn't tested, since that means posting. Bytes is the stricter count, so a draft that passes fits either way, at the cost of a rare early flag on a long draft full of accents or emoji.
